# Loan module: decisions, trade-offs and failure modes (Days 15–17)

The progression is deliberate: **calculate -> apply -> review**. None of these steps
moves money. These are educational lending rules, not a production underwriting model.
Changes are allowed; the last column explains what must change with them, not that every
alternative design is wrong.

## Day 15 — quotes, eligibility and amortization

| Decision                                                                                        | Why / trade-off                                                                                                                           | What breaks with a careless change                                                                                                                                                |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Money is integer paise, internally BigInt rational math; safe JSON numbers at the boundary.     | Avoids fractional-money and floating-point drift. BigInt formulas are harder to read and cannot be serialized directly.                   | Floating-point rounding can make installment totals inconsistent. Serializing BigInt throws; widening bounds without safe conversion can silently lose money precision.           |
| EMI uses the reducing-balance annuity formula; monthly rate is annual basis points / 120000.    | Explicit annual nominal versus monthly rate. No flat-rate interest, fees or APR model.                                                    | Using 12 instead of 1200 basis points, or omitting division by 12, produces a materially wrong loan quote.                                                                        |
| EMI and each month's interest round half-up; final installment settles the residual.            | Reconciles principal exactly and ends at zero. Final payment may differ from the advertised EMI.                                          | Rounding every payment identically without adjusting the final one leaves a balance or overcharges. Changing rounding requires updated schedules, totals and fixtures.            |
| Affordability uses the largest installment, not just EMI.                                       | Covers final-payment rounding. Slightly stricter by a few paise in some cases.                                                            | EMI-only checks can approve debt that exceeds the threshold in the final month.                                                                                                   |
| Fixed server-owned rate: 1200 bps (12%).                                                        | Predictable demo policy and no client rate tampering; no risk-based pricing.                                                              | Trusting a body-supplied rate lets callers price their own credit. A new server rate should affect only new quotes/applications, not stored snapshots.                            |
| Principal Rs 1,000–10 lakh; tenure 6–360 months.                                                | Bounds exposure, response size and exponent work; excludes otherwise possible loans.                                                      | Raising only schema limits leaves calculator/database limits inconsistent, causing errors. Removing tenure limits permits excessive CPU and response sizes.                       |
| Minimum income Rs 15,000; all monthly debt at most 40% of income; allowance rounded down.       | Simple explainable policy, inclusive equality. Income/debt inputs cap at Rs 10 lakh monthly. Not verified affordability.                  | Flipping `>` to `>=` wrongly rejects exact-boundary applicants; ignoring existing debt overstates affordability. Threshold changes need boundary tests and documentation updates. |
| Numeric JSON paise only; existing EMI defaults to zero; unknown fields dropped.                 | Strict input types, normalized defaults and mass-assignment protection. Typos may be silently dropped; strings require client conversion. | Trusting extra owner/status/rate fields enables privilege/business-rule bypass. Failing to normalize omitted zero causes false retry conflicts later.                             |
| Quote is authenticated but read-only, with no SQL or idempotency key.                           | Cheap experimentation without storing income or financial obligations. Token validity is not a fresh user lookup.                         | Accidentally writing from quote requests creates hidden obligations or privacy retention. Adding SQL requires changing explicit no-database HTTP tests.                           |
| Ineligibility is a 200 quote result with reasons; invalid input is 400.                         | A valid calculation can explain why it fails policy. Clients must examine eligibility, not merely HTTP success.                           | Treating every successful HTTP quote as approval accepts ineligible applications. Returning errors instead changes the contract and explanation UX.                               |
| Relative month numbers, no dates; zero interest supported internally but not client-selectable. | Tests reusable math without choosing due dates, calendar conventions or allowing zero-rate tampering.                                     | Adding due dates without handling month ends/time zones causes inconsistent schedules. Exposing calculator parameters bypasses server policy.                                     |

## Day 16 — durable pending applications

| Decision                                                                                        | Why / trade-off                                                                                                                                      | What breaks with a careless change                                                                                                                                                                        |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Recompute eligibility server-side before saving; never trust a submitted quote.                 | Prevents stale/forged quote acceptance. Declared income remains unverified.                                                                          | Accepting `eligible: true` or arbitrary saved EMI lets clients bypass policy. Verification is a separate requirement, not solved by this recomputation.                                                   |
| Save the full server-generated quote as JSONB alongside typed input columns.                    | Reproduces agreed terms without rerunning current policy. Duplicates data and stores a potentially large schedule; no policy-version identifier yet. | Recomputing on GET changes historical terms after a policy/math update. Independent edits of columns and snapshot can disagree; application writes must stay coordinated. Direct SQL is not tamper-proof. |
| `(user_id, idempotency_key)` unique constraint plus `ON CONFLICT DO NOTHING`.                   | Race-safe retries scoped to the caller, without account locks. A key is required even though submission does not move money.                         | An application-only precheck races and inserts duplicates. Globally unique keys let users collide. Update-on-conflict could overwrite existing terms.                                                     |
| On conflict, a new READ COMMITTED statement reads the winning row.                              | Avoids a no-op UPDATE solely to get its result. Adds a round trip on conflicts.                                                                      | Trying to read a concurrently inserted winner in the same statement's older snapshot may return nothing. REPEATABLE READ changes assumptions and needs explicit retry handling.                           |
| Replay compares principal, tenure, declared income and existing EMI after normalization.        | Same-key different requests are rejected with 422. No hash infrastructure is needed for four fields.                                                 | Omitting any field can acknowledge a materially different request. Treating changed input as a fresh application under the same key defeats retry semantics.                                              |
| Find replay before applying today's eligibility policy.                                         | Saved applications survive later policy changes. Replays represent saved terms, not new credit decisions.                                            | Revalidating first can reject a request that already succeeded or return new terms for an old application.                                                                                                |
| Failed attempts do not reserve keys; different keys may create multiple applications.           | Allows correcting invalid/ineligible submissions. Does not enforce one outstanding loan or retain a full failed-request response cache.              | Assuming key uniqueness equals an exposure limit allows repeated borrowing. Any real exposure cap must be checked atomically during approval/funding, not inferred from this table.                       |
| Ownership is enforced in SQL; customer reads return identical 404 for missing and unowned rows. | Protects against IDOR and existence probing. Even admins use a separate route for broader access.                                                    | Fetching by id alone leaks income/terms. Returning 403 for an unowned id confirms its existence.                                                                                                          |
| Pending application creation is one write, with no balance transaction.                         | An application is not a disbursement. Minimal locking, no funds affected.                                                                            | Adding balance or ledger writes outside an atomic transaction risks partial funding and money loss.                                                                                                       |
| Database bounds/FK/checks backstop validation; schema changes use migrations.                   | Stops invalid direct SQL and guarantees user linkage. Duplicated limits must stay aligned; FK restricts deleting referenced users.                   | API-only validation permits invalid rows through scripts/bugs. Editing old migrations does not update databases that already ran them. Test cleanup relies on FK-linked cascading TRUNCATE.               |
| Audit submissions via a small whitelist, excluding income and debt.                             | Security trace with less sensitive duplication. Still logs principal and tenure, and stores income in the owner/admin-only application.              | Copying whole bodies into audit logs exposes financial details, passwords or arbitrary payloads. Removing refusal logging loses attempted bypass evidence.                                                |

## Day 17 — admin review

| Decision                                                                                       | Why / trade-off                                                                                                                                             | What breaks with a careless change                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Dedicated admin detail/review endpoints, protected by both JWT role and current database role. | Admins may inspect applications without weakening customer ownership rules. One extra auth query; promotions require a new token.                           | JWT-only review allows demoted admins to act until token expiry. Removing service-side checks leaves unscoped repository access vulnerable to miswired/direct service calls.                                                         |
| Role check is fresh per request, not locked together with the decision.                        | Simpler modular design; prevents requests started after demotion from succeeding. An already-authorized in-flight request can still race a demotion.        | Claiming immediate atomic revocation overstates the guarantee. Stronger semantics need coordinated locking/version checks, not merely another lookup.                                                                                |
| No self-review, even if the borrower is an admin.                                              | Basic separation of duties, backed by database CHECK. Requires another admin; not a complete two-person-control system.                                     | Removing the service check permits self-approval attempts; removing the DB check too permits them through alternate write paths. Non-admin FK roles are not enforced by the database.                                                |
| Only `pending -> approved/rejected`; single conditional UPDATE.                                | PostgreSQL serializes row writers; one terminal decision wins. No reversal/edit/appeal API.                                                                 | Reading pending and then doing an unconditional UPDATE lets two reviewers overwrite each other. `WHERE status='pending'` is essential; row-shape checks alone do not prevent terminal-to-terminal changes by direct SQL.             |
| Natural review idempotency uses application id, reviewer, decision and normalized reason.      | No second key store is needed for a one-time state transition. Same result/actor/reason is a replay; anything else gets 409.                                | Comparing only status wrongly lets a different reviewer claim the decision. Ignoring the reason silently discards edits. Rewriting on retry changes timestamps and review history.                                                   |
| Reviewer identity, reason and timestamp are stored together; pending has none.                 | Complete decision metadata with DB consistency checks. Reviewer FK can restrict staff deletion; role changes remain possible.                               | A status-only update without the metadata fails the CHECK. Relaxing it allows unactionable approvals with no accountable reviewer or explanation.                                                                                    |
| Customer-visible reason is trimmed, 10–500 Unicode code points; SQL-unsupported text refused.  | Explains decisions without exposing staff ids or private underwriting notes. Minimum length does not prove a meaningful reason; no private notes field yet. | Treating the reason as a private note leaks secrets to the borrower. UTF-16 length checks disagree with PostgreSQL for emoji; null bytes or lone surrogates can cause database errors without edge validation.                       |
| Review response adds `review: null` or `{ reason, reviewedAt }`; staff UUID stays internal.    | Gives customers status explanations while reducing staff identifier exposure. Strict response-schema clients must accept the new field.                     | Leaking the full SQL row reveals internal ids/keys. Removing the new field breaks clients/tests that display explanations.                                                                                                           |
| Loan-review audit keeps decision and a bounded target id, not the narrative reason.            | Tracks successful/refused authenticated review attempts without duplicating sensitive notes. Does not audit detail reads.                                   | Capturing `req.params` only after response completion loses target ids when Express unwinds an error. Logging the whole reason duplicates customer-sensitive data.                                                                   |
| Audit remains post-response best-effort, separate from the state update.                       | Audit failures cannot turn a committed decision into a reported failure. A crash/write failure can lose its audit row.                                      | Treating this as a guaranteed financial audit is incorrect. Simply awaiting an audit write after committing could report failure even though approval happened; durable guarantees need an outbox or coordinated transaction design. |
| Rollback migration refuses when decisions exist.                                               | Avoids silently erasing review data. Operators must plan deliberate data handling before downgrade.                                                         | Automatically resetting statuses/dropping columns destroys business history. Removing the rollback guard makes a seemingly harmless migration command destructive.                                                                   |
| Approval never changes money or recalculates stored terms.                                     | Separates authorization from funding; easier to prove unchanged balances. Approved is not funded, and aggregate exposure is not checked.                    | Reusing deposit to fund a loan without dedicated ledger/funding/idempotency rules can create money or double-credit on retries. Saved quotes are estimates, not accrued loan balances.                                               |

## Shared architecture and test choices

- **Routes -> validation -> controllers -> services -> repositories.** SQL stays in the owning
  repository; auth user lookups go through the auth repository. More files, but rules can be
  tested independently. Putting SQL in controllers makes ownership/business rules easy to bypass.
- **Parameterized SQL.** Only fixed SQL text is assembled. Concatenating request values introduces
  injection risk, particularly because review reasons are arbitrary text.
- **Bounded, validated operations and existing whole-API rate limit.** No new per-user limiter,
  admin queue, application list or pagination yet. Adding an unbounded list would expose more
  sensitive data and create scaling work; designing that endpoint separately is intentional.
- **Unit tests plus real PostgreSQL/Supertest integration.** Mocks test branches; real tests prove
  SQL constraints, races, ownership and unchanged money. Mocks alone cannot prove row-update
  serialization. Handpicked concurrent tests improve confidence, not mathematical proof of all executions.
- **Safe test database reset.** Only `_test` databases can be wiped; asynchronous audit writes
  are flushed before resets. Bypassing the name guard risks real data; omitting the flush causes
  cross-test log leakage and flaky assertions.

## File responsibility map

| File(s)                                   | Consequence of a wrong change                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `loans.schema.js`                         | Invalid types/bounds, unauthorized writable fields or database-invalid text reach business rules. |
| `loans.calculator.js`                     | Wrong EMI, rounding or nonzero final balances; quote/schedule reconciliation fails.               |
| `loans.service.js`                        | Wrong rate, eligibility thresholds or affordability classification.                               |
| `applications.service.js`                 | Duplicate/conflicting requests misclassified; stale/current terms confused.                       |
| `applications.repository.js`              | Missing owner predicates leaks applications; missing pending predicate overwrites decisions.      |
| `reviews.service.js`                      | Stale roles, self-review or altered terminal decisions get accepted.                              |
| Controllers/routes and `modules/index.js` | Endpoints disappear or lose auth/validation; response/replay contract changes.                    |
| Audit actions/middleware                  | Sensitive metadata leaks, target ids disappear, or refused attempts stop being logged.            |
| Three loan migrations                     | Existing schemas diverge, bounds weaken or review history is erased on rollback.                  |
| Unit/integration tests                    | Regressions become invisible, especially concurrency and ownership failures.                      |

## Still not production lending

There are no verified income checks, credit bureau data, fees/APR disclosures, repayment
collection, interest accrual, overdue management, aggregate exposure limits, disbursement,
or formal audit retention. The saved snapshot is not a live outstanding balance. Keep these
limitations explicit when discussing the project in interviews.
